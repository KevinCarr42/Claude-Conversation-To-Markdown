**Rationale**: The entire point of Option 2 (LLM Proofreader) is that an LLM inherently knows that "Morue franche" is feminine and will produce "une grande Morue franche" without being told. The gender metadata in Option 4D was designed for a *rule-based* gender agreement system -- a system this project already tried and abandoned (see `lexical_constraints_options.md`, "Previously Attempted Solutions" table: "Gender correction in find/replace -- Abandoned -- Caused partial word replacements"). Re-investing 30 hours into infrastructure for an approach that already failed is the wrong call.

Waldorf's concern about "LLM as guess engine" and 2% error rates is legitimate but misapplied. The LLM is not guessing gender -- French gender is deterministic and LLMs handle it with near-perfect accuracy for well-known nouns. The real risk is hallucination (the LLM rewording the translation), which is mitigated by Statler's bounded validation (token survival rate, BLEU/similarity checks), not by a gender database.

---

## 3. The Compromise

Statler's urgency is correct: the codebase has real bugs producing wrong output today, and gating fixes on evaluation infrastructure is unjustified. Waldorf's structural instinct is correct: a raw function pasted into `translate_single` with no module boundary will create maintenance debt. The path forward takes Statler's sequencing (bugs first, ship fast, measure after) with Waldorf's structural discipline (new functionality gets its own module, validation gets explicit checks).

Specifically:

- **From Statler**: Bug fixes ship without an evaluation prerequisite. The proofreader starts with one provider. Gender is handled by the LLM, not by metadata.
- **From Waldorf**: The proofreader lives in its own module, not inline. Validation of proofreader output (token survival, similarity bounds) is explicit and testable. An evaluation dataset is built *in parallel* with the bug fixes, not *before* them.

## 4. Consequences

**Positive**:
- The MBART50 bug fix immediately restores generation parameter functionality for one of three model families.
- Boundary-aware postprocessing eliminates a class of partial-word replacement bugs.
- Fuzzy matching reduces the token-corruption fallback rate, meaning more translations preserve terminology.
- The LLM proofreader addresses gender/plural agreement without rule explosion.
- No 30 hours spent on gender metadata that may become obsolete.

**Negative**:
- Without an evaluation dataset landing *before* the bug fixes, there is no before/after measurement of the fix impact. This is acceptable because the bugs are provably wrong, but it means the quantitative improvement is not formally captured.
- The proofreader has a single provider dependency (Claude Haiku API). If that API is unavailable, the proofreader step is skipped entirely. This is acceptable because the proofreader is additive -- the existing pipeline works without it.
- Skipping gender metadata means if the LLM proofreader is later removed, there is no fallback gender handling. This is a conscious bet that the LLM approach is the long-term path.
